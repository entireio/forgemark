The two build layers

  1. Definitions + a forgemark output adapter (small, mostly in this repo). The runners are JSON, but forgemark needs a machine-readable monitor mode: reduce a results.Doc to the runner's {"value": <n>,
  "rationale": "..."} last-JSON-line contract. A forgemark report --emit monitor (or a --format entire) over the existing engine + internal/results. Cheap, and it's the seam everything else hangs off.

  2. The runtime (the real work, needs Entire). Every stock runner uses the read-only claude sandbox. forgemark is different: it needs the forgemark binary, network egress to the target forge, and ideally
  regional placement (forgemark's whole methodology caveat is "run close to the target"). That's a new runner profile, and it's exactly where Entire's regional clusters + mirrors are the differentiator.

  - A proper non-prompt kind. I saw hints of agent_runner, trail_runner, and one script_runner reference but no command_runner/exec_runner, so a measured/exec runner kind looks like a genuine gap
  forgemark would be the first real user of.

  1. Definitions + a forgemark output adapter (small, mostly in this repo). The runners are JSON, but forgemark needs a machine-readable monitor mode: reduce a results.Doc to the runner's {"value": <n>,
  "rationale": "..."} last-JSON-line contract. A forgemark report --emit monitor (or a --format entire) over the existing engine + internal/results. Cheap, and it's the seam everything else hangs off.

  2. The runtime (the real work, needs Entire). Every stock runner uses the read-only claude sandbox. forgemark is different: it needs the forgemark binary, network egress to the target forge, and ideally
  regional placement (forgemark's whole methodology caveat is "run close to the target"). That's a new runner profile, and it's exactly where Entire's regional clusters + mirrors are the differentiator. Two
  ways to get the runtime.kind:
  - Reuse prompt_runner as an MVP: a runner whose prompt is "run forgemark ..., emit the result JSON as the last line" (works with today's adapter, if the sandbox allows egress).
  - A proper non-prompt kind. I saw hints of agent_runner, trail_runner, and one script_runner reference but no command_runner/exec_runner, so a measured/exec runner kind looks like a genuine gap forgemark
  would be the first real user of.

  Sequencing

  1. forgemark monitor-output mode — the adapter (this repo, no Entire dependency).
  2. CI/Gate proof — wire it into GitHub Actions on top of open PR #6's threshold flags: forgemark runs, emits the monitor value, gates the PR. Proves the signal with zero new Entire infra.
  3. Native Entire runner — the regional, egress-capable runtime that runs forgemark in-region and posts monitors to the Trail. The strategic headline.

  1. Does a Gate already threshold a trail_monitor (so throughput < X fails a Trail), or is Gate still to build? That decides whether forgemark just emits and rides existing gating, or we build the gate too.
  2. Is there an exec/command/script_runner runtime, or would forgemark be the case that justifies one? This is the biggest scope fork.
  3. Sandbox reality: can a runner sandbox make outbound git connections and be pinned to a region? That's the gating constraint on the native runner.
