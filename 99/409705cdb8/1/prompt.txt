## Phase 2 — Engine instrumentation: the Sink (B)

Design principle: the engine stays per-target and per-level; **level lifecycle is not an engine event** — the caller (CLI loop or server coordinator) calls `RunLevel` itself, so it already knows level start/end and gets `LevelResult` as the return value. The only hook the engine needs is the per-sample hot path:

```go
// Sink observes every recorded sample, including warmup samples, live.
// OnSample is called concurrently from up to `concurrency` agent goroutines
// and must be cheap and non-blocking.
type Sink interface {
    OnSample(s Sample)
}
```

Implementation: `agent` gains a `sink Sink` field; every `a.samples = append(a.samples, s)` site (5 in agent.go, 4 in session.go) is replaced by one method:

```go
func (a *agent) record(s sample) {
    a.samples = append(a.samples, s)
    if a.sink != nil { a.sink.OnSample(exportSample(s)) }
}
```

`a.samples` remains the authoritative post-hoc source for `summarize` — **CLI behavior is untouched** (nil sink, one nil-check per op, zero allocations).

**Mechanism recommendation: direct callback into a mutex-protected aggregator, not a channel.** Justification: sample rates are modest (≤ a few hundred ops/sec per target — each sample is a full git push round-trip), while a `sync.Mutex` sustains millions of lock/unlock per second even contended. The server-side sink does ~10 integer increments and one `append` to a bucket slice under the lock (&lt;1µs). A buffered channel would need a drainer goroutine, a drop policy, and shutdown ordering, and would still allocate for batching — complexity with no payoff at this volume. No per-agent batching needed either.

`Sample` (exported): `Offset time.Duration; Dur time.Duration; Res Outcome; Op OpKind; Msg string`. Offset is relative to level start; the collector timestamps buckets itself, so no wall-clock field needed.

**Review gate:** unit test — run a fake sink through a `record`-exercising path; existing bench tests still green.

## Phase 3 — Server: run manager, coordination, API, aggregation

New package `internal/server` (stdlib only: `net/http`, `embed`, `encoding/json`).

### 3a. Multi-target coordination (C)

Because `RunLevel` is a synchronous fixed-duration call (`warmup+duration` timeout inside), **the level barrier is just a WaitGroup per level** — start each level simultaneously across targets, wait for all, then advance:

```go
// runmgr.go — coordinator goroutine per run
for li, c := range w.Concurrency {
    run.emit(levelStartEvent{li, c, w.Warmup, w.Duration})
    var wg sync.WaitGroup
    for _, t := range run.liveTargets() {
        wg.Add(1)
        go func(t *targetState) {
            defer wg.Done()
            t.collector.startLevel(li, time.Now())
            res, err := t.runner.RunLevel(run.ctx, c)
            if err != nil { t.dead = true; run.emit(targetErrorEvent{t.ID, li, err.Error(), true}); return }
            t.results = append(t.results, res)
        }(t)
    }
    wg.Wait()
    run.emit(levelResultEvent{...per-target results...})
    if run.ctx.Err() != nil || run.allDead() { break }
}
run.finish() // persist + run_done event
```

Alignment is exact at level start; level end skew is bounded by in-flight push completion (pushes are `PushContext`-bound, cancel promptly at the level deadline).

**Hard-error policy (recommendation): continue the others.** A target failing `NewRunner` (bad URL/auth/probe) or `RunLevel` (agent construction) is marked dead, emits a fatal `target_error` event, and is skipped in later levels; the run keeps its remaining targets — a comparison run where one forge is misconfigured still yields the other curves. The run fails as a whole only when *all* targets are dead. `NewRunner` for all targets executes concurrently in the run goroutine (the entiredb probe is a network call), so `POST /api/runs` returns immediately after validation; setup failures arrive as events.

The coordinator uses a `levelRunner` interface so the demo target (Phase 6) plugs in:

```go
type levelRunner interface {
    Label() string
    RunLevel(ctx context.Context, concurrency int) (bench.LevelResult, error)
}
```

One `RunManager` holds `map[string]*Run` under a mutex; a single active run at a time is enforced (409 on concurrent POST) — this is a load generator, overlapping runs corrupt each other's numbers. Finished runs stay in memory for the session (bounded, e.g. last 20) and on disk forever.

### 3b. Live aggregation (E)

Per target, per run — `collector.go`:

```go
type collector struct {
    mu        sync.Mutex
    levelIdx  int
    levelT0   time.Time
    cur       bucket            // counters + latencies landing in the current second
    window    [10]bucketLats    // ring of last-10s OK latencies for rolling percentiles
}
func (c *collector) OnSample(s bench.Sample)      // implements bench.Sink: increments + append, under mu
func (c *collector) snapshot(now time.Time) BucketStats // called by the 1s ticker
```

**Recommended approach: exact per-tick sort over a 10-second rolling window.** A ticker goroutine per run fires every second; for each target it locks, swaps out the current bucket, pushes its latencies into the ring, concatenates the ring (≤ 10s × few hundred ops = a few thousand float64s), sorts, and takes p50/p95/p99 with the existing `percentile()`. Sorting 3k floats is ~100µs once per second — nothing. No t-digest, no heap tricks; exact and ~40 lines. Throughput = OK count in the 1s bucket (per-second, not windowed, so spikes are visible). Buckets during warmup are emitted too (UI shades the warmup region using `level_start.warmup_sec`).

### 3d. SSE event schema (D)

Standard SSE frames: `id: &lt;seq&gt;\nevent: &lt;type&gt;\ndata: &lt;json&gt;\n\n`, heartbeat comment every 15s. Every event appended to `run.events []event` (seq-numbered); a subscriber first receives a replay from `Last-Event-ID+1` (or 0), then live events — this makes browser reconnect and late-join free, since `EventSource` resends `Last-Event-ID` natively. Buffer is small: ~1 bucket event/sec + a handful of lifecycle events (an hour-long run ≈ 3600 events ≈ a few MB; acceptable, cap at 100k defensively).

```
event: hello
data: {"run_id":"fmxyz","state":"running","started_at":"2026-07-23T10:00:00Z",
       "workload":{...as posted...},
       "targets":[{"id":0,"name":"gitlab","label":"https://gitlab.example"},
                  {"id":1,"name":"entire","label":"https://us.entire.example"}],
       "levels":[1,8,32]}

event: level_start
data: {"level_index":0,"concurrency":1,"at":"...","warmup_sec":10,"duration_sec":60}

event: bucket            // once per second while a level runs
data: {"level_index":0,"t":1784000123,
       "targets":{"0":{"ops":42,"ok":41,"cas":1,"err":0,
                       "p50_ms":88.1,"p95_ms":140.2,"p99_ms":190.0,
                       "clones":0,"clone_ok":0,"clone_err":0},
                  "1":{...}}}
       // percentiles = rolling 10s window; keys are target ids; a dead target is absent

event: level_result
data: {"level_index":0,"concurrency":1,
       "targets":{"0":{&lt;bench.LevelResult JSON, existing tags&gt;},"1":{...}}}

event: target_error
data: {"target":1,"level_index":0,"message":"info/refs probe: HTTP 401: ...","fatal":true}

event: run_done
data: {"state":"done","results_file":"forgemark-fmxyz.json","at":"..."}
       // state ∈ done|cancelled|failed (failed = all targets dead)
```
